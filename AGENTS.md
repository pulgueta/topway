# AGENTS.md

## Overview

Topway is a native **macOS menu bar app** (SwiftUI) for monitoring and managing Railway projects, services, environment variables, and deployments — a lightweight alternative to keeping the Railway dashboard open. It talks directly to Railway's public GraphQL API.

## Build & Run

The app is an Xcode project with one local package, `Packages/TopwayCore`. There are no third-party packages. Open `topway.xcodeproj` in Xcode and run (scheme `topway`), or from the CLI:

```sh
# Build (with no signing; signing needs the certificate of team 7QNFW3929Z)
xcodebuild -project topway.xcodeproj -scheme topway -configuration Debug CODE_SIGNING_ALLOWED=NO build

# Build into a known location, then launch
xcodebuild -project topway.xcodeproj -scheme topway -configuration Debug \
  CODE_SIGNING_ALLOWED=NO -derivedDataPath build build
open build/Build/Products/Debug/topway.app

# Test the core
swift test --package-path Packages/TopwayCore

# Format and lint
swift format --in-place --recursive topway Packages
swift format lint --recursive --strict topway Packages
```

- **Deployment target: macOS 26.2** (Tahoe). The UI uses Liquid Glass APIs like `.buttonStyle(.glassProminent)` that require the macOS 26 SDK — older Xcode/SDKs will not compile.
- **Swift 6** with strict concurrency and `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`: every type in the app target is `@MainActor`-isolated unless explicitly marked otherwise. `TopwayCore` has no default isolation and uses `Sendable` types.
- The app is **sandboxed** (`topway/topway.entitlements`) with hardened runtime; only `network.client` is granted.
- **Sign in with Railway needs a client ID.** Put `RAILWAY_OAUTH_CLIENT_ID = <id>` in `Config/OAuth.local.xcconfig` (gitignored; the README tells how to make a Native OAuth app). Never commit a client ID. With no value (CI, a build from source), the app builds and offers only sample data. To build with no client ID while the local file exists, add `RAILWAY_OAUTH_CLIENT_ID=` to the `xcodebuild` command.

## Architecture

The app is built around a single observable state object injected through the SwiftUI environment.

- **`AppState`** (`@MainActor @Observable`) — the single source of truth. Holds `projects`, `isLoading`, `errorMessage`, credentials, and the auto-refresh task. Every user action goes through one of its `async` methods, which call its `RailwayDataSource` (`RailwayClient`, or `SampleDataSource` in sample mode), then convert thrown `RailwayError`s into `errorMessage` strings (the client throws; AppState never re-throws to the view). Most write methods call `loadProjects()` afterward to reconcile UI with the server. Injected via `.environment(appState)` in `topway/App/TopwayApp.swift` and read with `@Environment(AppState.self)`.

- **`RailwayClient`** (`Sendable` struct in `TopwayCore`) — stateless GraphQL transport against `https://backboard.railway.com/graphql/v2`. Every call is a `POST` with a `Bearer` token. All operations funnel through the private `execute` generic, which throws typed `RailwayError`s for HTTP and GraphQL failures. A cancelled request is `RailwayError.cancelled` and shows no message. **User input is always passed as GraphQL `variables`, never string-interpolated into the query** — this is intentional (injection/escaping safety); preserve it when adding operations.

- **Logs** use WebSockets, with polling as the fallback. `GraphQLWebSocket` sends one `graphql-transport-ws` subscription to `wss://backboard.railway.com/graphql/v2`; Railway reads the token from the `Authorization: Bearer` header of the upgrade request, and `connection_init` has no payload. `RailwayDataSource.logs` takes a token provider (`token: @Sendable () async throws -> String`) and asks it at each socket connect and each poll, because a stream can run longer than one access token (`LogTokenTests`). The protocol rules are pure code in `GraphQLSubscription` (tested without a network). `SocketKeepalive` sends a protocol `ping` every 20 s and drops a socket with no message for 20 s after a ping (Railway sends no pings of its own). `LogRecovery` (pure, tested) decides each step: after a live socket drops it connects again with a backoff (2, 4, 8, 16, then 30 s; a payload resets it; after 5 reconnects in a row that do not connect, it polls), after 3 live passes with no payload it polls (network error) or stops (bad data), it polls when the socket never connected, and it stops on a Railway error. Polling sends one `deploymentLogs`/`buildLogs` request each 5 s, keeps going after a network error, tries the socket again every 60 s, and ends a build log when the deployment status shows the build is finished. `GraphQLWebSocket` moves frames through `MessageTransport`, so tests use `ScriptedTransport` and `ScriptedConnector`. `LogDeduplicator` removes repeated lines (same timestamp, message and severity, in the last 1,000 lines). `RailwayClient` and `SampleDataSource` take a `sleep` closure, so tests do not wait. `LogsView` keeps the newest 1,000 lines in `LogBuffer` and stops the stream when it closes. When you add a subscription, use the WebSocket first and check the document on the public endpoint with no token: a valid document answers "Not Authorized", "not found" or "Problem processing request", and a wrong document answers "Cannot query field".

- **Metrics** come from the Railway `metrics` query (`RailwayDataSource.fetchMetrics`): `CPU_USAGE` (vCPU), `MEMORY_USAGE_GB`, `NETWORK_RX_GB` and `NETWORK_TX_GB` for one service in one environment. `MetricWindow` gives the start date and `sampleRateSeconds` (30, 60 or 240, as the Railway CLI does). `ServiceMetrics` (pure, tested) gives one `MetricSeries` for each `MetricKind` and adds the results of one measurement at each time. `MetricKind.formatted` gives the text of a value. `MetricsView` loads on open, on a new time range and on **Refresh**; it does not poll. `MetricCard` draws the chart with Swift Charts (a system framework). `SampleDataSource+Metrics` gives a wave that comes only from the service, the environment and the date.

- **Environments** — `EnvironmentsView` (project **Manage** menu > **Environments**) lists the environments of a project from `appState.projects`. `environmentCreate` takes `projectId`, `name` and an optional `sourceEnvironmentId`; with a source, Railway copies its services, variables and settings. `environmentDelete` takes the ID. `EnvironmentRules` (pure, tested) gives the clean name, the name problem (empty, or a name that the project has) and the harm of a create: low for an empty environment, medium for a copy, because the services then deploy. A delete is high harm with the environment name typed. `Project.environmentList` leaves out the environments that Railway deleted. `AppState.createEnvironment` and `deleteEnvironment` load the projects again.

- **Service settings** — `ServiceSettingsView` (service **Manage** menu > **Settings**) reads `serviceInstance(environmentId:serviceId:)`: `serviceName`, `source` (shown, not changed) and the cases of `ServiceSetting` (build command, start command, root directory, healthcheck path). `ServiceSettings.changes(from:)` (pure, tested) gives only the changed values, so a save sends `serviceUpdate(id:input:{name})` for a new name (all environments) and `serviceInstanceUpdate(serviceId:environmentId:input:)` for the other settings (one environment). An empty field goes as `null`. A save is medium harm. To add a setting, add a case to `ServiceSetting` (the raw value is the field name on Railway) and to the response type. Railway has no branch in `ServiceInstanceUpdateInput`, so Topway does not change the source or the branch.

- **Domains** — `DomainsView` (service **Manage** menu > **Domains**) reads the `domains(projectId:environmentId:serviceId:)` query: `serviceDomains` (Railway domains, `DomainKind.railway`) and `customDomains`. `serviceDomainCreate` makes a Railway domain, and `DomainRules.canAddRailwayDomain` permits one for each service in an environment. `customDomainCreate` adds a domain of the user, and its answer has `status.dnsRecords`. `CustomDomainStatus.records` (tested with the shape of the Railway answer) gives the `DNSRecord` rows: the records of Railway, then a TXT record `railway-verify=<token>` at `verificationDnsHost` until `verified` is true, as the Railway CLI shows them. `Domain.status` is `needsRecords`, `waitingForCertificate`, `certificateFailed` (certificate status `ISSUE_FAILED`, with `DomainStatus.advice`) or `ready`. `DomainRules.problem` checks a typed name before the request. `serviceDomainDelete` and `customDomainDelete` take the ID. Each add and each delete is medium harm. Topway shows a domain as text and does not open it.

- **Database templates** — **Add service** has the source **Database** (`DatabaseTemplate`: `postgres`, `mysql`, `redis`, `mongo`; the raw value is the template code on Railway, as in the Railway CLI). `RailwayClient.deployDatabase` reads `template(code:) { id serializedConfig }` **with no token** (the template is public), gives each variable its default as its `value` (`TemplateConfig.filled`, pure, tested; all other fields stay as Railway gave them), and sends `templateDeployV2(input: { projectId, environmentId, templateId, serializedConfig })` with the token. `deployDatabase` returns when Railway accepts the deploy, and gives the `workflowId`. `waitForDatabase` then asks `workflowStatus(workflowId:)` each 2 seconds, at most 30 times and at most 60 seconds, with a 10 second limit for each request: `Complete` gives `.complete`, the status `Error` throws, and all other answers wait (`WorkflowResult.step`). **After Railway accepts a deploy, Topway never reports the add as failed because a status request failed**: a network error, a GraphQL error or the end of the wait gives `DatabaseDeployResult.pending`, and the message says that the database can show later and that the user must not add it again. A cancelled wait is `RailwayError.cancelled`. `AppState.startDatabase` runs in the confirmation dialog, which closes when Railway answers. `AppState.finishDatabase` runs in `AddServiceView`, which shows "Railway adds the database…" and **Close** in place of the add button; it always loads the projects and leaves the form. A template variable with no default that is not optional stops the deploy (`TemplateConfigProblem`), because Topway has no screen to ask for it. A database is medium harm, because Railway bills its usage.

- **Reference variables** — a value can hold Railway references: `${{api.VAR}}` (a service), `${{shared.VAR}}` (a shared variable) and `${{VAR}}` (the same service). Spaces inside the braces are permitted. `fetchVariables` sends `unrendered: true` (as the Railway CLI does for its editor), so a reference keeps its template and a save does not replace it with the rendered value. `fetchProjectVariables` reads the shared variables (`variables` with no `serviceId`) and the variables of each service in one request, with the aliases `s0`, `s1`… (the service IDs go in variables); Topway passes `Project.serviceList(in:)`, the services that are in the environment. A sealed variable has the value `null`; its name stays. `fetchVariables` gives it the value `nil` (`EnvironmentVariable.isSealed`): `VariableRow` shows "Sealed" with a lock and has no **Show** and no **Copy**, **Copy all** gives a `#` comment line with the name only (`dotenvLine`), and the editor starts empty and cannot save an empty value over it, also when **Add variable** has its name (`EnvironmentVariable.permitsSave(of:as:sealedNames:)`; `ServiceView` passes the sealed names). A save replaces the value, and Railway keeps the variable sealed. `fetchProjectVariables` keeps it as a target with an empty value. The sample data has one sealed variable (`STRIPE_SECRET_KEY` of the storefront API); like Railway, a new environment does not get a copy of it. The rules are pure code in `TopwayCore/References` (tested): `VariableReference.all(in:)` finds each reference with its range (the full text between the braces must be `NAME`, `shared.NAME` or `service.NAME`, with spaces only next to the braces; a service name is an ASCII letter, then letters, digits, `_` and `-`, as the Railway CLI accepts in `auto_wrap_reference`; a variable name starts with a letter or `_`; anything else, such as `secret(32)` or a stray brace, gives no target, so no part of a malformed value shows), and `ProjectVariables.status(of:from:services:)` gives `found`, `missingService` (the service name must be exact), `missingVariable`, `setByRailway` (a `RAILWAY_` name that the list does not have) or, with no loaded variables, `notChecked`. `Variable.references` in the schema has no documented format, so Topway does not use it. `ServiceView` loads the project variables after the variables of the service, and `VariableRow` shows one `ReferenceLinkRow` for each target (`ReferenceLink.links`). A link has names only, so it shows while the value is hidden; never add a value to its label. In `EditVariableView`, `ReferenceMenu` (**Insert reference**: a service, then a variable, from `ProjectVariables.referenceGroups`) puts `ReferenceTarget.template` in place of the selection, and `ReferenceSuggestions` shows the matches of `ReferenceCompletion` (the text after an open `${{` before the cursor) and completes the reference. When the cursor is in a reference with a `}}` on the same line, the completion replaces the rest of that reference; the text after an open `${{` stays. The editor reads the cursor from `TextEditor(text:selection:)`.

- **Service links** — `ServiceLinksView` (project **Manage** menu > **Service links**, `NavigationDestination.serviceLinks`) is read-only. It loads `fetchProjectVariables` for one environment and shows `ServiceGraph` (pure, tested) as text: one `ServiceLinkSection` for each node (the services of the environment, then the shared variables when a link uses them), with **Uses** and **Used by** lines. An edge is one pair of nodes with the sorted names of the variables that have the references; two services can link to each other, a same-service reference gives no edge, and a name with no service gives `missingService`. A list, not a drawing, so it stays readable for 2 to 15 services and VoiceOver reads each edge (`ServiceGraph.sentence(for:)`). When a reload removes the selected environment, `EnvironmentSelection.reconciled` (pure, tested) selects the first available one, and the screen drops the links and the load of the removed one; with no environment, it shows "No environments". `ServiceView` uses the same rule: it drops the variables and the loads of the removed environment, goes back to its overview, closes an open dialog (the dialog names the removed environment) and, with no environment, shows "No environments" and disables **Settings**, **Domains** and **Redeploy**.

- **GraphQL variables** are `[String: JSONValue]`. `execute(query:variables:)` takes text values. `execute(query:json:)` takes an input object or a `null`. All user input still goes in variables.

- **Deployment actions** — `Deployment.availableActions` (pure, tested) gives the actions of the **Manage** menu of a deployment row: **Cancel deployment…** (`deploymentCancel`) for a build or a deploy in progress, **Roll back…** (`deploymentRollback`) when Railway gives `canRollback: true` in the `deployments` query, and **Remove deployment…** (`deploymentRemove`) for a deployment that runs, crashed or sleeps. Each is medium harm. Restart (`deploymentRestart`) and Redeploy (`serviceInstanceRedeploy`) are older actions with their own buttons. A new action of `AppState` goes in an extension file (`AppState+DeploymentActions.swift`) and calls `run` or `runAction`, which report each failure in the same way. A new operation of `RailwayClient` or `SampleDataSource` goes in an extension file too.

- **Spend** (`RailwayDataSource.fetchSpend`, `TopwayCore/Spend`) is for the workspace. `RailwayClient` sends two requests: `workspace.customer` gives `currentUsage` (the cost in US dollars, which Railway calculates and keeps in a cache), `billingPeriod` and `usageLimit` (whole US dollars; a `softLimit` of 0 is not set); then `usage` (with `includeDeleted: true`, as the Railway CLI does) gives the totals of `UsageKind` from the period start to now (vCPU-minutes, GB-minutes, GB). A "Not Authorized" answer here is about billing access (Railway gives it only to workspace admins), so `AppState.fetchSpend` shows `Spend.failureMessage`, does not set `isTokenRejected` and does not refresh the token (`withAccessToken(retryingRejected: false)`). **Topway has no price table and calculates no cost.** Do not add prices: show only a cost that Railway gives. `Spend` (pure, tested) has the days left, the limit use and the dollar text. `SpendRow` in the projects list opens `SpendView`.

- **Incident banner** — `RailwayDataSource.fetchOpenIncident()` sends the `platformStatus` query to the same GraphQL endpoint **with no `Authorization` header** (Railway answers it with no token; `execute` takes `token: nil`). Never add the token or a variable to this request; `PRIVACY.md` says that it has none. `PlatformStatus.openIncident` (pure, tested with a recorded answer) gives the incident when its status is not `RESOLVED`. `PlatformIncident.link` opens only an HTTPS page on railway.com, or else `https://status.railway.com`. `AppState.loadProjects()` starts `checkIncident()`, `MainView` calls `refreshIncident()` each time the window opens (auto refresh is off by default), and `IncidentCheck.isDue` limits it to one request in 5 minutes; `shouldAnnounceIncident(id:)` lets VoiceOver say each incident only one time; a failed check keeps the last answer and shows no error. `MainView` shows `IncidentBanner` for `appState.visibleIncident` below `SampleDataBanner`. `SampleDataSource` sends no request and gives one incident with the text "Sample incident: …". The status page (`https://status.railway.com/api/status`) also has JSON, but it is about 570 KB for each request and has no schema, so Topway does not use it.

- **`TopwayCore/Models` and `TopwayCore/API/Responses`** — one type in each file. `Decodable` structs mirroring Railway's Relay-style `edges`/`node` connection shape, one `*Data` wrapper per query/mutation, plus UI models (`EnvironmentVariable`, computed display helpers on `Deployment`). Convenience extensions (`Project.serviceList`, `Workspace.projectList`) flatten connections for the views.

- **Navigation** — there is **no `NavigationStack`**. `MainView` holds a `NavigationDestination` enum and switches between `.main` / `.usage` / `.addService` / `.environments` / `.serviceLinks` / `.service` with animated transitions inside a fixed **360×480** popover (`Layout`). `ServiceView` has its own steps (`ServiceDestination`: `.overview` / `.editVariable` / `.logs` / `.settings` / `.domains`), and its overview has the tabs `ServiceTab.variables`, `.deployments` and `.metrics`. Escape (`onExitCommand`) navigates back one step.

- **Welcome window** — Topway has no Dock icon (`LSUIElement`), so at launch the user sees only the menu bar icon. `TopwayApp` has a `Window` scene (`id: "welcome"`, `WelcomeView` in `topway/App`) that shows only at the first launch and tells the user (and App Review) where the icon is. Its `defaultLaunchBehavior` is `.presented` while the `UserDefaults` key `welcomeWindowShown` (`WelcomeView.shownKey`, read with `@AppStorage`) is not `true`, else `.suppressed`. `WelcomeView` sets the key in `onAppear` and calls `NSApp.activate()`, so the window comes to the front. `restorationBehavior(.disabled)` keeps it closed at the next launch, and `windowResizability(.contentSize)` keeps its size. The icon in the window is `MenuBarLabel` with an empty (healthy) `HealthSummary` and `.labelStyle(.iconOnly)`, so it stays the same as the menu bar icon. There is no setting to show the window again. To see it again in development, delete the key and launch: a signed build (sandboxed) keeps it in `~/Library/Containers/com.pulgueta.topway/Data/Library/Preferences/com.pulgueta.topway.plist`, and a build with `CODE_SIGNING_ALLOWED=NO` (not sandboxed) keeps it in `~/Library/Preferences/com.pulgueta.topway.plist`. Give `defaults delete` the full path, because `defaults delete com.pulgueta.topway` changes the container file when it exists.

- **Design** — read `DESIGN.md` before you change a screen. The rules that matter most: every action has a text label, and no action shows only on hover; the only icon-only buttons are back and close, with an accessibility label and `.help`; each screen uses `ScreenLayout` with `ScreenHeader` (top) and `ActionBar` (bottom); Liquid Glass is only on the control layer (`.buttonStyle(.glass)` / `.glassProminent` in the bars, inside one `GlassEffectContainer` per bar), never on a list row; lists use `LazyVStack`; sizes come from `Layout`; UI copy is ASD-STE100 Simplified Technical English.

- **Accessibility** — `docs/accessibility.md` has the evaluation for the App Store Accessibility Nutrition Labels and the manual checks. Keep these rules when you change a screen: a button that shows in each row names its item in the accessibility label, and `accessibilityInputLabels` gives Voice Control the visible text; a status is never color only; each custom animation and transition reads `accessibilityReduceMotion`; an error that shows away from the control posts an `AccessibilityNotification.Announcement`, but only while its window appears active (`appearsActive` is in the ID of the `.task` that posts, so a closed menu bar window says nothing and the error is said when the window opens); the dialog hides the content behind it (`destructiveConfirmation`). Pure wording for a label, such as `HealthSummary.statusDescription`, goes in `TopwayCore` with tests.

### Key conventions & gotchas

- **Sign in with Railway is the only way to connect.** There is no API token field and no Workspace ID field. Topway is a Railway OAuth app of the type Native (Public): PKCE S256, no client secret, redirect URI `https://topway.pulgueta.com/oauth/callback`. The pure rules are in `TopwayCore/OAuth` (tested); the app part is in `topway/SignIn`.
  - `AuthorizationRequest` builds the URL of `https://backboard.railway.com/oauth/auth` with a random `state`, the S256 challenge (`PKCE`), `prompt=consent` (Railway gives a refresh token only with it) and the scopes `openid email profile offline_access workspace:admin` (`RailwayOAuth.scopes`). Without `email` and `profile`, `me { workspaces }` is empty. `workspace:admin` is a maximum: Railway gives the role that the user has in each workspace that the user selects, and Topway deletes services and projects and reads billing, which only an admin can do. `FormEncoding` encodes all values (also `+`).
  - `WebSignIn` runs `ASWebAuthenticationSession` with the HTTPS callback `.https(host: RailwayOAuth.callbackHost, path: RailwayOAuth.callbackPath)` and the key window (the menu bar window or Settings) as the anchor. Topway registers no URL scheme and runs no local server. Associated Domains (`webcredentials:topway.pulgueta.com` in `topway/topway.entitlements`, and the `apple-app-site-association` file on that host) give the redirect only to an app of team 7QNFW3929Z. This closes the custom-scheme risk (RFC 8252, section 8.6) only when the Railway OAuth app has no other redirect URI, so remove `topway://oauth/callback` before the App Store release. `docs/release.md` lists what must stay in place. The session is not ephemeral, so a user who is signed in to Railway in the browser sees only the consent page, and an email sign-in link works. A closed window is `OAuthError.cancelled` and shows no message. `SessionGeneration` (tested) changes on a new sign-in, a sign-out and sample mode, but not on a refresh: `signIn()` checks it after each wait and before it saves the tokens, `loadAccount()` drops an answer of an earlier generation, and a sign-out or sample data cancels the open `WebSignIn`. Settings shows `signInError` in the Account section, with **Try again**.
  - `AuthorizationCallback.code(in:state:)` checks the address (`https`, `RailwayOAuth.callbackHost` and `callbackPath`, no port and no user name), the state (also on an error), the `iss` value when it is there, and the code. `RailwayOAuthClient` posts a form to `https://backboard.railway.com/oauth/token` with `client_id` and `code_verifier` (exchange) or `refresh_token` (refresh). Never send a client secret: Railway refuses a Native app that sends one. A 400 or 401 answer with the code `invalid_grant` (RFC 6749, 5.2; `TokenErrorResponse`) is `OAuthError.rejected`: the tokens are deleted and the user signs in again. Another code, for example `invalid_client` or `invalid_request`, is `requestRefused(code)`: the tokens stay and the message gives the code. 429 and 5xx are `serverError`, and the sign-in stays. Never show the body of a token answer, only the code. When the Keychain does not save renewed tokens after two writes, the tokens stay in memory and `errorMessage` says that a new sign-in can be necessary at the next launch.
  - `OAuthTokens` (access token, refresh token, expiry) is one Keychain item (`railwayOAuth`, JSON) via `KeychainStore`, so the two tokens change together. `AppState.tokens` is the in-memory copy. Never log a token, and never put one in a URL.
  - `AppState.withAccessToken` gives each request its token. It refreshes a token that expires in less than 5 minutes, and when Railway answers "Not Authorized", it refreshes one time and sends the request again (Railway did not run the first request). Only one refresh runs at a time (`tokenRefresh`): Railway rotates refresh tokens, and a use of a rotated refresh token ends the whole authorization. When the refresh fails with a network error before the token expires, the request uses the current token. When Railway does not accept the refresh token, `endSession` removes the sign-in and the start screen shows `sessionNotice`. A request that started in an earlier `SessionGeneration` (a sign-out, a new sign-in or sample data while it waited) ends as `RailwayError.cancelled`, with no message and no retry (`SessionGeneration.permitsRetry`), so a late answer never sends a request again with the token of another account. `endSession` also stops a running confirmation action and closes the dialog, and a log stream gets no token of a later session. A refresh that Railway refuses ends the sign-in only in the session where the refresh started (`SessionGeneration.permitsSessionEnd`), so a late refusal does not close the window of **Sign in again**. A refresh that succeeds while the same tokens stay is kept also after **Sign in again** starts, because Railway can rotate the refresh token.
  - Railway has no revocation endpoint (the discovery document has none, and `/oauth/token/revocation` answers 404). **Settings > Account > Sign out…** removes the Keychain item and the workspace choice from this Mac. Its footer tells the user to remove the access on the Apps page of the Railway account settings.
  - `AppState.init` deletes the API token of earlier builds (Keychain item and `UserDefaults` key `railwayToken`) and does not use it. With no saved sign-in, it removes `workspaceId`, so an upgraded user sees the start screen.
  - The build gives the client ID: `Config/OAuth.xcconfig` (committed, empty value) includes `Config/OAuth.local.xcconfig` (gitignored) and is the base configuration of the app target; `topway/Info.plist` (merged with the generated Info.plist, and a membership exception of the synchronized folder) has `RailwayOAuthClientID = $(RAILWAY_OAUTH_CLIENT_ID)`. `RailwayOAuth.clientID(fromInfoValue:)` gives `nil` for an empty or not expanded value. Then `AppState.canSignIn` is `false`, the start screen offers only **Try with sample data** and says why, and Topway does not read the saved sign-in.

- **Workspaces come from the sign-in.** After a sign-in, `RailwayClient.fetchAccount` reads `me { name email workspaces { id name } }`, which has only the workspaces that the user selected on the consent page. `WorkspaceChoice.selection` (tested) keeps the saved workspace when the account still has it, or uses the only one. With several, `AppState.needsWorkspace` is `true` and the projects screen shows `WorkspacePickerView`. `AppState.selectWorkspace` saves `workspaceId` in `UserDefaults`, drops the projects of the earlier workspace and loads the new ones. **Settings > Account** shows the name and email, a **Workspace** picker and **Sign out…**. Auto refresh, alert and mute settings stay in `UserDefaults`.

- **A rejected token must never trap the user.** Railway answers a bad token with HTTP 200 and the GraphQL error "Not Authorized"; `RailwayError.init(graphQLErrors:)` turns that message (and an HTTP 401) into `.unauthorized`. `AppState.isTokenRejected` is `true` while `errorMessage` comes from that error, after one refresh did not help (for example a workspace that the user did not share, or an action that the role does not permit). `ErrorStateView` gets its buttons from `RecoveryRules` in `TopwayCore` (tested): a rejected token offers **Sign in again** and **Try with sample data**; other failures offer **Try again** and **Open Settings**; sample mode offers only **Try again**. While the token is rejected, **Refresh** in the projects header is hidden and **Refresh Projects** (Command-R) is not available. A failed **Sign in again** shows its message on the open screen, because the start screen does not show while the earlier sign-in stays. While the token is rejected, the message goes in `signInAgainError` (a new `errorMessage` removes it), so the rejected state and **Sign in again** stay; `ErrorStateView` and the projects `ErrorBanner` show and announce it.

- **Pass closure literals to SwiftUI APIs**, for example `Button("Save") { save() }` and `set: { setValue($0) }`. Xcode 26.6 on CI crashes when a main-actor method reference is passed as a `Button` action or a `Binding` setter.

- **Confirmations use `GlassConfirmationDialog` through `destructiveConfirmation(...)`, never `alert`/`confirmationDialog`.** Call `appState.confirm` with a `ConfirmationRequest`, and set its `HarmLevel` (low: no dialog; medium: names the service and environment; high: exact name typed). `MainView` presents the dialog. Native dialogs present in a separate window and steal key focus, which dismisses the `MenuBarExtra(.window)` popover out from under them. Keep all confirmation UI within the popover.

- **Railway API limitations** (reflected in the UI): project _creation_ isn't available on the public API — the app deep-links to the Railway dashboard instead. Service creation is from a GitHub repository, a Docker image, or one of the four database templates. Soft-deleted projects keep coming back from the API with a `deletedAt` set; they're filtered out in `Workspace.projectList`.

- **Auto-refresh** is a single cancellable `Task` loop in `AppState` (`startAutoRefresh`/`stopAutoRefresh`/`restartAutoRefresh`). Toggling the setting or interval restarts it. `initializeAutoRefresh()` runs from the `.task` of the `MenuBarExtra` label (`MenuBarLabel`). The label shows at launch, so the refresh starts at launch, not when the popover opens. It also loads the projects once.

- **Health and alerts** are pure logic in `TopwayCore/Health`. `HealthSummary(projects:)` gives the menu bar health. `AlertSnapshot` keeps the last settled state (deployment ID and status) of each service; in-progress statuses do not replace it. `AlertSnapshot.update(with:mutedProjectIds:)` gives the alerts of a new load. `AppState.sendAlerts(for:)` runs after each successful `loadProjects()` and keeps the snapshot (`alertSnapshot`). Set `alertSnapshot = nil` when the data source or the workspace changes; a `nil` snapshot gives no alerts. `AlertNotifier` sends `UNUserNotificationCenter` notifications; in sample mode the subtitle is "Sample data". `NotificationPresenter` (set in `TopwayApp.init`) shows banners while the app is active; the center keeps a weak reference, so `TopwayApp` keeps it. `alertsEnabled` and `mutedProjectIds` live in `UserDefaults`. Settings asks for notification permission only when the user turns alerts on. Launch at login uses `SMAppService.mainApp` in `LaunchAtLoginToggle`, which reads the system state and keeps no copy.

- **Problem reports go through GitHub Issues only.** The app collects no data and has no crash SDK. **Settings > Help** (`HelpSettingsSection`) opens the link from `IssueReportLink` (`TopwayCore/Reports`, tested), which fills the device fields of a form in `.github/ISSUE_TEMPLATE` from `DeviceDetails`. The query item names are the field ids of the forms, so change them together. GitHub fills only text fields from a link, so the device fields are `input` fields, not dropdowns. The `data-mode` field is "Sample data" in sample mode, else "Signed in with Railway" or "Not signed in" (`DeviceDetails.isSignedIn`, from `AppState.isSignedIn`). The `architecture` field reads the hardware (`hw.optional.arm64` and `sysctl.proc_translated`, mapped by `CPUArchitecture(arm64:translated:)`), not `#if arch`, so an Intel build with Rosetta gives "Apple silicon (arm64) with Rosetta". Never add a token, a Workspace ID or project data to the link.
